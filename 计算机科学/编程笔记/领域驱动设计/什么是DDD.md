DDD（Domain-Driven Design，领域驱动设计）是由 Eric Evans 在 2003 年同名著作中提出的一套软件设计方法论。它的核心思想是：软件的核心复杂度来自业务领域本身，而不是技术实现，因此设计应该以业务领域为中心。

## 什么是业务领域
业务领域指一个组织或系统所从事的经营活动、业务范围及其内在规律的总和。它回答的是：这个软件到底在解决什么现实世界的问题。

- 业务范围：组织做什么、不做什么。例如电商平台涉及商品、订单、支付、物流；银行涉及账户、交易、风控、清算。
- 业务规则：领域内必须遵守的约束。例如“订单金额不能为负”“库存不足时不能下单”“同一用户当日提现不超过5万”。
- 业务概念：领域内的核心名词及其关系。例如订单、客户、商品、合同、保单。
- 业务流程：业务活动的先后顺序和协作方式。例如“下单→支付→发货→收货→售后”。
- 业务目标与价值：领域存在的意义，例如“降低交易成本”“提高履约效率”。

### 如何定义业务领域的软件模型
软件模型是业务领域的抽象表达。

1. 业务概念 → 领域对象
业务中的名词变成模型中的实体、值对象。例如：
业务概念“订单” → Order 实体
业务概念“金额” → Money 值对象
业务概念“客户” → Customer 实体

2. 业务规则 → 不变量与约束
业务规则变成模型中的校验逻辑和业务方法。例如：
“订单总额 = 各明细金额之和” → Order.calculateTotal()
“已支付订单不能取消” → 状态机中的状态转移约束

3. 业务流程 → 领域服务与应用服务
跨多个对象的业务活动变成领域服务；编排用例的流程变成应用服务。例如“下单”流程涉及库存扣减、订单创建、支付发起，由应用服务编排。

4. 业务边界 → 限界上下文
不同业务子领域有不同含义和规则，这决定了系统如何划分模块和边界。例如“商品”在销售上下文和库存上下文中含义不同。

5. 业务语言 → 统一语言
业务专家和技术团队共用一套术语，模型中的命名直接来自业务语言，减少翻译损耗。
